# Требования: оформление B2B-заказа

## Цель

Дать представителю организации-клиента оформить заказ по условиям действующего договора (цены прайс-листа, кредитный лимит, отсрочка) без участия менеджера, если сумма не превышает порог согласования.

## Границы

**В scope:** создание, просмотр, отмена заказа; проверка лимита; резервирование; публикация событий.
**Вне scope:** оплата, логистика, формирование закрывающих документов (выполняются в смежных системах).

## Роли

| Роль | Права |
|---|---|
| Закупщик | Создаёт и отменяет заказы своей организации |
| Руководитель | Согласует заказы выше порога |
| Бухгалтер | Просматривает заказы и счета организации |
| Менеджер платформы | Просматривает заказы клиентов, вручную меняет статус |

## Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Система должна создавать заказ по договору, принадлежащему организации пользователя |
| FR-02 | Система должна рассчитывать цену позиции по прайс-листу, привязанному к договору |
| FR-03 | Система должна проверять, что сумма заказа не превышает доступный кредитный лимит договора |
| FR-04 | Система должна резервировать остатки по всем позициям до подтверждения заказа |
| FR-05 | Заказ выше порога согласования должен переходить в статус AWAITING_APPROVAL и ожидать решения руководителя |
| FR-06 | Система должна отклонять недопустимые переходы статусов с кодом 409 |
| FR-07 | При отмене заказа система должна снимать резерв и публиковать событие OrderCancelled |
| FR-08 | Повторный запрос создания с тем же Idempotency-Key не должен создавать второй заказ |
| FR-09 | Пользователь одной организации не должен видеть заказы другой организации |
| FR-10 | Система должна публиковать события жизненного цикла заказа для ERP, WMS и уведомлений |

## Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Производительность | POST /orders: 95-й перцентиль не более 500 мс при 200 запросах в секунду |
| NFR-02 | Доступность | 99,9% в месяц для API создания заказа |
| NFR-03 | Надёжность | Событие публикуется не реже одного раза; потеря событий недопустима (RPO = 0 для заказов) |
| NFR-04 | Идемпотентность | Ключ хранится 24 часа |
| NFR-05 | Безопасность | Аутентификация OAuth 2.0 (JWT), TLS 1.2+, проверка принадлежности ресурса организации на каждом запросе |
| NFR-06 | Аудит | Каждое изменение статуса фиксируется: кто, когда, из какого и в какой статус; хранение 5 лет |
| NFR-07 | Масштабируемость | Горизонтальное масштабирование Order Service без потери порядка событий одного заказа |
| NFR-08 | Совместимость | Добавление необязательных полей в API не требует новой версии |

## Критерии приёмки

**FR-03**

```
Дано: у договора доступный кредитный лимит 100 000 ₽
Когда: закупщик отправляет заказ на 184 500 ₽
Тогда: API возвращает 422 с кодом CREDIT_LIMIT_EXCEEDED,
       заказ не создаётся, резерв остатков не выполняется
```

**FR-08**

```
Дано: заказ создан с Idempotency-Key = K
Когда: клиент повторно отправляет тот же запрос с ключом K
Тогда: API возвращает 201 с тем же orderId, новый заказ не создаётся
```

**FR-08 (конфликт)**

```
Дано: заказ создан с Idempotency-Key = K
Когда: клиент отправляет запрос с ключом K и другим составом позиций
Тогда: API возвращает 409
```

**FR-09**

```
Дано: пользователь организации A
Когда: запрашивает заказ организации B по orderId
Тогда: API возвращает 403 (или 404, если политика скрывает существование ресурса)
```
